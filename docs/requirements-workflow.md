# 需求整理、追问与恢复

## 这一步能做什么

用户描述要做的应用，ProductManager 整理并保存需求文档。信息不够时，页面列出具体问题，
用户补充回答后继续整理。每轮都保存新版本，不覆盖旧需求。直到没有待确认问题，返回
`ready_for_design`。需求就绪后，ProjectManager 自动创建下一版 Plan，将一个设计任务派给
SolutionArchitect，固定引用这版 `app_spec`，预期产出为 `system_design`。这一步只保存任务，
不调用架构师模型、不生成设计或代码，也不代表应用已经完成。

设计计划和任务保持 `pending`，BuildRun 仍为 `running / pm`，直到后续实现真正的设计任务领取。
页面以 `design_pending` 显示“已派给架构师，等待处理”，并保留需求正文。重复请求只返回原任务。
若需求已保存但派工失败，页面显示需求就绪，可点击“继续派给架构师”，不会重新调用需求模型。

本次处理的是需求阶段的补充和修正；不包含开发进行到一半后的跨阶段需求变更、设计重算、
代码重建或发布。未回答的问题由模型结合原需求继续整理，结构校验不会证明语义一定正确。

## 完整流程

1. 保存用户消息，并由 ProjectManager 分类为 `product_change`。
2. 创建或复用同一项目的 queued BuildRun，针对指定消息建立初始 Plan 和需求 Task。
3. 领取 Task，再登记唯一有效的执行编号。模型调用期间不持有数据库事务。
4. ProductManager 生成经过结构校验的 `app_spec`，先保存执行草稿。
5. 在同一事务中保存正式成果、TaskResult，完成 Task、Plan 和本次执行。
6. 如果有 `open_questions`，记录待回答关联并在页面显示问题；否则跳到第 10 步派工。
7. 用户回答时，将回答消息、新 Plan、新 Task 和原需求的回答关联一起提交。
8. 新 Task 明确引用原 `app_spec` 的编号，只使用那份原需求和这条回答，不混入之后的消息。
9. 生成新的 `app_spec`，其 `upstream_item_ids` 指向原需求。回到第 5 步，允许多轮追问。
10. ProjectManager 校验已保存需求的归属、TaskResult、完成状态和问题清单，将设计 Plan 与
    SolutionArchitect Task 一起提交，返回设计计划和任务编号。不创建新的 BuildRun 或用户消息。

补充后的 Plan 版本递增，但旧 Plan、Task 和成果都保留。BuildRun 在需求就绪或等待回答时
仍为 `running / pm`；页面从已保存的数据还原更细的进度，不把整个构建提前标记为成功。
LangGraph 负责连接步骤和选择分支；数据库记录才是恢复依据，不依赖进程内图状态。

## 重复点击、失败和超时

- 一个 Task 同时只有一个有效执行。重复启动正在执行的任务返回 409，不再调用模型。
- 每次执行有效期为 10 分钟。调用失败会记录失败并释放执行位置；进程突然退出时，等待
  有效期结束后才能恢复。当前没有自动重试、续期、后台队列或持续运行的 worker。
- 恢复必须提交页面查询到的 `execution_id`。恢复会创建新执行编号，保留之前的执行记录。
- 旧执行晚到时不能发布成果，也不能把新执行标记为失败。
- 草稿已经保存但正式成果保存失败时，恢复优先使用草稿，不再请求模型。
- 需求已完成、只剩设计派工未成功时，用原 `message_id` 重试工作流即可，无需执行恢复编号。
  工作流读取正式需求后只重试派工；并发请求通过项目/运行锁和 Plan 版本唯一约束串行校验。
- 已完成任务可读取原结果。相同请求编号、相同回答重复提交，只得到原来的补充计划。
  同一份需求提交另一份回答会被拒绝，需要刷新并回答当前这一轮的问题。
- 有效期结束并不等于远端模型请求已停止。若旧请求仍在远端运行，恢复可能产生第二次模型
  请求；执行编号保证旧结果不能覆盖新结果，不承诺模型计费“恰好一次”。

## 页面怎么使用

保留原有 mock 页面。前端使用 `VITE_PROJECT_DATA_SOURCE=api` 时，项目页显示真实需求工作台。
从首页创建项目后，点击“开始整理需求”。回答待确认问题后点击“提交补充回答”；任务失败
或过期后点击“恢复执行”。页面刷新只读取进度和对话，不会自动触发模型调用。

请求由 FastAPI 在线程池内同步执行，处理时页面轮询进度。若代理提前断开连接，应先刷新
进度，再按页面状态继续，不能把 HTTP 连接断开直接视为任务失败。

## 接口

以下路径均以 `/api/v1/projects/{project_id}` 开头，沿用现有登录和项目归属校验。

| 方法与路径                                                 | 用途                                                                  |
| ---------------------------------------------------------- | --------------------------------------------------------------------- |
| `GET /requirements`                                        | 读取当前需求文档、待确认问题和恢复编号                                |
| `POST /build-runs/{run_id}/requirements`                   | 用 `message_id` 开始/继续本轮任务；恢复时另传 `recovery_execution_id` |
| `POST /build-runs/{run_id}/requirements/{item_id}/answers` | 提交 `content`、`client_message_id`，保存补充计划并执行               |

消息保存、消息分类和创建 BuildRun 继续使用原接口。回答接口直接关联当前问题，不把
“CSV”这样的简短回答重新当成一条独立需求分类。客户端在重复提交同一份回答时必须复用
`client_message_id`，不要每次重试都生成新编号。

`GET /requirements` 的状态：`not_started` 等待开始、`pending` 等待执行、`running` 正在执行、
`retry_available` 可显式恢复、`needs_user_input` 等待回答、`ready_for_design` 需求就绪但尚未派工、
`design_pending` 设计任务已创建并等待处理、`stopped` 已结束或不属于当前需求流程。

工作流响应保留原需求的 `plan_id`、`task_id` 和 `configuration_item_id`，并新增可空的
`design_plan_id`、`design_task_id`。交接成功时两个设计编号同时返回，`outcome` 仍为
`ready_for_design`（描述需求已就绪）。查询接口的顶层 `plan_id/task_id` 表示当前设计计划/任务，
其嵌套 `result` 保留原需求及设计任务的完整关联。刷新只是查询，不会给历史需求自动派工。

## 数据库与启动

本次设计派工复用现有 Plan、Task 和 TaskResult，没有新增表或迁移，也没有修改本机已有业务数据。

新增迁移 `5c9d3e7f1a2b`，上一版为 `4e8a2c6d0f1b`，新增两张表：

- `task_execution`：各次执行的编号、有效期、状态、错误和恢复草稿。
- `requirement_clarification`：原需求、原 Task、补充回答和后续 Plan 的准确关联。

迁移不改写旧成果。迁移前已经保存、仍可用且带问题的需求，首次回答时补建关联。
启用新接口前，在 `apps/backend` 安装锁定依赖并对目标数据库执行 `alembic upgrade head`。
对其他环境迁移前，请先确认数据库备份和连接目标。
