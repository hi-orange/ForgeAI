# ForgeAI 测试工程师重设计：目标与接续开发说明

日期：2026-10-13。本文记录用户确认的下一阶段方向，供换电脑拉取代码后继续实现。

**状态：工程执行内核与依赖调度已重构；本文描述的完整 QA 闭环尚未实现。不要把本文或现有 smoke 通过当作该目标已完成。**

## 1. 最终目标

ForgeAI 的测试师应对标真实测试工程师，负责：

**需求分析 → 用例设计 → 测试实现 → 实际执行 → 缺陷反馈 → 修复复测 → 回归验收。**

测试师验证获批功能是否齐全、行为是否正确、用户流程是否联通，不审计工程师的编码先后顺序。
采用“需求驱动的可重复测试 + 真实应用探索”，而不是仅阅读工程师的 smoke 输出并写报告。

## 2. 当前代码已完成什么

- PM、架构师、工程师、测试师的责任与工具边界已有显式角色契约。
- 工程师采用同一模型的观察、工具动作、反馈循环，不再强制先生成逐文件计划再交给嵌套模型写整文件。
- 工程写入经过暂存、执行租约与原始内容校验，保留可恢复版本、调用预算和停止条件。
- PRD 的功能列表不再直接决定施工顺序。工程师提交可持久化的依赖计划；平台验证需求覆盖、依赖环及冻结设计中的前置约束，只执行就绪任务。
- 视觉基础先建立或验证复用；认证仅在获批需要时引入。可调整待做计划，但不能删除或篡改已完成任务，也不能重置预算。
- 有独立 Test Engineer、冻结验收计划、准确源码/测试身份、完整检查和桌面/移动截图门禁。

现有测试师仍主要是“读取产物 + 调用现成检查 + 记录缺陷/报告”，不是本文目标中的完整测试实现者。

## 3. 已确认的缺口

- `app/services/acceptance_testing.py` 中的 `build_acceptance_test_plan` 当前按验收条目生成逻辑测试描述，主要指向 `run_check(all)`，没有独立编写并执行完整业务用例的能力。
- `app/tools/test_engineer.py` 中的 `_validated_report` 存在兼容分支：缺少 `test_results` 时，从需求级结果补出测试级结果。必须防止这种推导被当作逐项执行事实。
- 测试师尚无受限的测试代码写入工具和独立测试套件生命周期。
- 当前完整检查和截图不能证明每条核心业务链、权限边界、异常路径及持久化行为都被实际执行过。

以上定位基于当前代码。接续实现前重新核对，勿仅凭旧文档假设实现。

## 4. 四角色责任

- PM：定义产品承诺、用户流程、约束、共享视觉方向及可观察验收条件，不安排编码顺序。
- 架构师：确定接口、数据所有权、权限及必要前置契约，不替测试师规定通过结论。
- 工程师：实现应用、编写必要单元测试、联调自测、修复缺陷；开发期 smoke 不代替独立验收。
- 测试师：拥有独立测试场景、测试代码与验收证据，检查最终产品行为，不修改业务源码，不降低获批标准。
- 平台：负责隔离执行、权限、身份绑定、证据记录、预算、恢复及交付门禁，不能由模型自述替代实际结果。

测试不是全部交给测试师。工程师自测与独立 QA 应互补，避免机械地为每个功能重复生成三层测试。

## 5. 用例与脚本分层

### 5.1 需求场景

从获批需求及验收条件设计，不以“代码已经实现什么”为覆盖范围。每条场景至少包含：

- 稳定用例 id、关联功能/验收 id、用例目的。
- 前置条件、所需测试数据、操作步骤、可观察预期结果。
- 正常、异常、权限或回归等分类，以及执行所需环境。

应用尚未完成时可以设计场景，不应提前猜测选择器和接口路径。
不得借设计测试引入未获批功能；需求歧义或验收冲突应显式报告。

### 5.2 执行实现

应用可运行后，根据真实接口和页面，把场景落成可重复的 API 或浏览器测试。
选择器、路径、启动方式属于执行适配；不能因实际实现不同就偷偷改掉预期结果。
测试代码放入独立、受限的测试区域，不与业务源码写权限混用。

### 5.3 探索与回归

在核心用例之外，按相关风险探索空输入、重复提交、刷新、返回、会话失效等行为。
发现问题后保存复现证据，并尽可能沉淀为稳定回归用例。
需要判断视觉和开放式交互时可以使用浏览器智能体；适合确定性断言的行为优先用确定性执行器。

## 6. 测试师运行内核

根据当前覆盖情况与真实反馈，选择下一项必要动作：

1. 找出尚未覆盖的需求或用户流程。
2. 设计/补充用例并检查其预期是否有获批依据。
3. 编写或适配测试脚本，在隔离环境执行。
4. 分析失败究竟来自业务实现、测试脚本、环境还是验收冲突。
5. 记录缺陷，或继续验证；修复后复测并做必要回归。

不规定每轮必须走完全部步骤；已有有效测试可以直接执行复用。失败循环必须有预算，不无限重试。

## 7. 证据与权限门禁

- 业务源码对 QA 只读；QA 仅可写自己的测试资产、隔离测试数据及报告。
- 每次执行绑定准确 `code_item_id/source_hash` 和测试资产版本；历史结果不能套用到新版本。
- 用例的执行状态、命令/动作、断言结果、输出和必要截图/轨迹由执行器记录；模型可以解释，不能伪造执行事实。
- 通过、失败、阻塞、未执行必须区分。没有证据不能补成通过，环境不可用也不是业务功能通过。
- 测试中允许对隔离应用创建、修改、删除测试数据，不得访问真实生产数据或进行真实付款/发信等外部副作用。
- 复测沿用原来的业务预期；修复测试脚本须产生新测试版本并重跑，不能覆盖旧证据。
- 删除用例、降低断言或改动业务预期不属于普通脚本修复，必须进入明确的复核/争议处理。

## 8. 冻结与版本兼容：实现前必须处理的边界

当前架构和技能约束将验收计划视为平台拥有的冻结产物，工程师和测试师不能直接改写。
新目标要求 QA 编写测试，不能直接打开现有冻结目录的写权限来绕过这个约束。

应区分：获批产品标准、版本化测试场景/脚本、绑定某次执行的冻结测试快照。
QA 可产出草稿和新版本，由平台校验、冻结并登记；运行中的快照不可变，工程师始终无权弱化独立测试。
测试脚本错误与产品需求改变也应分开：执行适配修正不应自动要求重新批准产品，但预期改变必须受控。

这属于接续实现要明确并更新的合同，不是本提交已经提供的能力。
修改相关所有权或状态转换前，按仓库规则同步架构约束、技能参考、运行时 schema 和测试。
保留旧产物读取能力，但不得让旧的隐式结果合成路径绕过新的通过门禁。
如引入持久化表/字段，添加数据库迁移；若扩展版本化 JSON 契约，明确版本、旧格式读取和升级边界。

## 9. 推荐实现顺序

每次只落地一个可测试的完整增量，不同时铺设大量未使用抽象：

1. 梳理现有验收计划、检查运行器、测试师工具及报告注册/发布门禁，确认复用点。
2. 明确场景、测试版本和执行证据的数据契约，补覆盖校验及禁止合成通过结果的回归测试。
3. 提供测试师受限写入测试资产与执行测试的能力，复用现有隔离容器和浏览器基础设施。
4. 打通一条完整样例链：设计用例、测试实现、真实失败、工程修复、复测通过。
5. 接入缺陷复测、相关回归、恢复和预算控制，再补充探索性测试与报告展示。

不必先新建更多角色，也不要把测试师固定成只跑 `all` 的报告生成器。

## 10. 完成标准

- [ ] 每个获批功能都有可追溯的验收场景，未覆盖项能被门禁识别。
- [ ] 核心跨功能用户流程有实际执行证据，而非仅检查页面渲染或 health 接口。
- [ ] 测试师可以生成、版本化并实际运行独立测试；业务源码仍不可写。
- [ ] 逐项结果引用运行器证据，伪造 test id、旧源码证据、未执行却通过等情况被拒绝。
- [ ] 业务缺陷、脚本错误、环境阻塞及标准冲突可区分，均有明确后续路径。
- [ ] 修复后使用新源码身份复测，历史证据与测试版本保持可追溯。
- [ ] 必需用例通过、无阻断缺陷，且不存在被当作通过的未执行/阻塞项，才允许交付。
- [ ] 真实容器/API/浏览器集成测试验证执行链；mock 测试不能冒充真实端到端验证。

最小演示应用应包含获批的身份与私有记录能力，验证：登录 → 新建记录 → 列表读取 → 刷新仍存在 → 另一账号不能读取；另测错误凭据、未登录访问及无效输入。
这只是验证平台的样例，不是给所有生成应用强制添加登录。

## 11. 接续开发入口

路径均相对于仓库根目录：

- `apps/backend/app/services/acceptance_testing.py`：冻结验收计划生成与读取。
- `apps/backend/app/schemas/acceptance_test_plan.py`、`test_report.py`：测试及报告契约。
- `apps/backend/app/agents/test_engineer.py`、`agents/prompts/test_engineer.py`：测试师循环和提示。
- `apps/backend/app/tools/test_engineer.py`：现有工具与结果校验，包括需改造的结果合成分支。
- `apps/backend/app/services/test_engineer.py`：QA 生命周期与成果提交。
- `apps/backend/app/tools/checks.py`：现有隔离检查与源码身份入口。
- `apps/backend/tests/test_acceptance_testing.py`、`test_test_engineer.py`、`test_requirements_loop.py`：重点回归入口。
- `apps/backend/app/generation/delivery.py`、`generation/engineering/`、`orchestration/code_engineer.py`：已重构的工程执行链，继续保持其边界。

提交前建议执行后端完整 pytest、Ruff、mypy，以及根目录 `node scripts/check-encoding.mjs`。
真实 Docker 集成测试需准备对应镜像并显式启用 `FORGEAI_TEST_DOCKER=1`；未运行时必须如实注明。
未经用户授权不要调用付费模型作探测，不操作开发者真实数据库来验证流程。

## 12. 研究依据与边界

- [MetaGPT 论文](https://arxiv.org/html/2308.00352v7) 与 [QA 实现](https://github.com/FoundationAgents/MetaGPT/blob/main/metagpt/roles/qa_engineer.py)：有测试生成、执行和反馈循环，但所查实现主要是 Python 文件级测试，不等同于完整 Web 业务验收。
- [OpenHands QA 实现规则](https://github.com/OpenHands/extensions/blob/main/skills/qa-changes/SKILL.md)：强调启动应用、真实浏览器/API/CLI 验证，并区分 CI、代码审查与 QA。
- [WebGen-Bench](https://arxiv.org/html/2505.03733v2)：按需求构造操作及预期结果，由浏览器智能体执行用例；这是外部评测流程，不代表被测平台内部已有该能力。
- [IWC-Bench](https://arxiv.org/html/2609.15387v1)：探索真实交互并利用覆盖反馈补充验证，说明固定用例之外还有探索性测试价值。

本文方案是结合这些证据与 ForgeAI 约束的工程设计，不是某篇论文的完整复现，也未证明真实模型成功率或成本已经改善。
